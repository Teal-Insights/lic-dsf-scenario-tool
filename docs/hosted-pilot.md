# Illustrative hosted pilot candidate

This optional mode is under review. An illustrative, unaccepted pilot instance is running for demonstration; it rejects workbook uploads. The acceptance gates below still apply. Own-workbook operation stays in the local app. The hosted operator must separately obtain the exact official template and review its hosting rights; no workbook is included in source or image.

`python -m lic_dsf.hosted_server` uses Waitress 3.0.2. Configure DSF_ORIGIN to one HTTPS origin, DSF_DATA_DIR to a disposable dedicated state directory, and DSF_OFFICIAL_WORKBOOK to the read-only official file. Start only one process/replica. A process lease rejects a second instance. Never expose the desktop HTTP server for this purpose. The explicit loopback-only HTTP constructor option exists for development tests; the production factory never enables it.

The entry page describes server processing before a visitor enters. An unguessable Secure/HttpOnly/SameSite cookie selects a per-visitor database and an independent token protects API requests. Unknown routes, arbitrary workbook upload, and private-journal writes are rejected. Scenario-file import remains browser-side; Save sends its illustrative assumptions, label and explanations to the server. Do not enter confidential data.

Access lasts one hour from entry. A five-second sweeper deletes expired directories, including pending work. Cleanup is targeted within a further75seconds while bounded operations finish, not an unconditional filesystem guarantee. Cleanup failure blocks further API use/new visits and is retried. Explicit deletion is available even when visit quotas have been exhausted. Restart invalidates sessions and clears prior visitor directories. Downloads remain on the visitor's device. No backup or retained history is configured.

Admission limits: twelve simultaneous visits,24new visits/hour globally,240API calls/minute globally,600calls/visit,60saved edits,8calculations,30chart/download requests,4cases/comparison. These protect a small pilot's resource envelope, not fair access under abuse. One calculation runs at a time. Calculations and exports run in disposable children with parent-loss/deadline guards and CPU/output-file limits; Linux also applies address-space limits. Request/result scratch files are removed afterward; child logs are discarded.

The deployment templates add bounded tmpfs, memory/CPU/process limits, read-only root, dropped privileges, internal container networking and disabled container logs. The app port is not published. Host Caddy connects to the inspected internal container address after scoped host firewall rules are installed; follow [the deployment procedure](../deploy/README.md). An internal bridge alone does not prevent container access to host services. These templates require actual Linux/container and TLS-proxy testing before use. Pin the base image and inspect the full build inventory before publication. Verify host/proxy/provider logging and firewall behavior independently. Mac calculation evidence does not establish Linux equivalence, fresh Excel verification, browser usability or absolute deletion/no-egress guarantees.

The existing local numerical regression script and tests/test_hosted.py provide reproducible starting checks. Supply DSF_TEST_WORKBOOK outside source to run the hosted API tests. The deployment gate additionally requires two-visitor live-server tests, both chart views, complete exports, failure injection, restarted/expired work cleanup, source/build-content review, rights and spending approval.

## Bounded export waiting successor

The hosted page submits each chart/packet once to POST/api/export-jobs with a unique request key, then polls authenticated GET/api/export-status and retrieves GET/api/export-result. Safe GET429/503 responses carry Retry-After and are retried automatically. Saves and other edits are never automatically retried. A lost submit response is recovered through the visitor’s GET/api/export-current and matching request key, never by replaying the POST.

The FIFO queue holds at most25jobs including ready results, with one queued/running job pervisitor. New submission can replace only that visitor’s ready result after admission/quota checks pass. Ready bytes can be fetched again for up to60seconds without rerender or additionalcharge. Jobs expire at600seconds overall. Each completed render consumes one export slot; failure/cancel before completion and GETpolls/retries consume none. Slot30remains reserved for ZIP. Queued work has priority over new uncached calculations and legacy synchronous exports.

The interface shows a fixed waiting panel, current queue position and Cancel button. Cancellation submits once and kills/reaps the tracked running renderer; if cancellation cannot be confirmed, the interface says so. Visit deletion, expiry and restart discard jobs and ready bodies. The GET/body wait has a620second client bound plus bounded cancellation/recovery cleanup. A source/comparison change stops the obsolete export. No visitor can inspect/cancel/retrieve another visitor’s job.

Only one existing bounded rendering child runs. The configured32MiBper-result and25globaljob ceilings imply up to800MiBof retained ready bodies before accounting for active workers/serverbuffers. This is a bound to validate on Linux, not capacity evidence. The normal UI renders both views after each of the three teaching calculations: a25personfullflow is150SVGexports plus25ZIPs. Its local source-bound automatic-flow receipt executes the actual waiting JavaScript overHTTP with stubbedDOM; actualbrowser/TLS/Linux acceptance is separate.

Container startup MUST use Compose init:true or docker run --init. The existing lifetime guard rejects parentPID1; the init process makes the application a normal guarded parent and reaps children. Do not weaken parent_probe to acceptPID1. Queue cancellation, like visit deletion, remains admitted after global/pervisitrequest limits while retaining JSON/body/host/origin/token checks.


## Host proxy and internal networking

Use the dedicated internal bridge and host Caddy procedure in [deploy/README.md](../deploy/README.md). Internal-network port publication was unreliable in the tested Docker 29 configuration; this recipe instead uses the inspected current container IP as `DSF_UPSTREAM` and has no `ports` mapping. Do not infer connectivity or isolation from a Compose declaration alone.

Before starting or restarting the application, install IPv4 and IPv6 host INPUT rules scoped to that bridge: allow conntrack `ESTABLISHED,RELATED` replies and drop bridge-originated `NEW` connections before broader accepts. This permits replies to host-initiated Caddy connections while blocking new application connections to host services. Keep Docker's internal forwarding restriction, set the container resolver to `127.0.0.1`, and test actual DNS and IPv4/IPv6 behavior. Do not attach another external network or weaken the parent-lifetime guard to make startup pass.

A recreated container may have a new IP. Inspect it, validate the literal upstream and Caddy configuration, then reload the proxy deliberately. Firewall ordering, restart behavior, host access refusal, DNS refusal and functioning proxy/calculation/export traffic need an exact-host receipt. Setup fails closed if either firewall family, bridge identity or upstream address cannot be established. No setup instruction authorizes changes to unrelated host firewall rules.
