# How we use the Digital Public Goods Standard

**This tool has not been certified or formally recognized by the Digital Public Goods Alliance (DPGA). We do not claim full compliance with the Digital Public Goods Standard.** We use the standard as a reference for good practices while developing this early-stage tool through iterative co-design with ministries of finance, international financial institutions and other stakeholders.

Our aim is practical: make the software understandable, inspectable and reusable, protect analytical work, and help users assess what the results can and cannot establish. The table below builds on our earlier assessment, showing how the tool relates to each indicator, where evidence exists and what remains unresolved. It is our self-assessment, updated **13 September 2026**, not an external assessment or a compliance score.

The [official DPG Standard](https://www.digitalpublicgoods.net/standard) has nine indicators, with three parts under indicator 9. Formal recognition follows a successful review. That review covers the core solution; it does not certify every organisation's local implementation. Our installation and security evidence therefore remains necessary in its own right.

## What this assessment covers

This register covers the general, single-user local application, its documentation, scenario-file exchange and briefing exports. The briefing includes PDF reports, PNG/SVG charts, CSV/Excel tables, comparison JSON and file fingerprints. The separate scenario file carries reusable inputs for the identical workbook; a briefing packet is not an importable scenario or a full backup.

Evidence from earlier tested builds supports only the behavior and environments actually checked. Alpha.1 has source-check and documentation-build CI evidence. Alpha.2, the built-in walkthrough release, requires its own source checks, independent artifact review and desktop acceptance; prior browser evidence does not cover its rebuilt artifacts. At package assembly, Windows execution, downloaded Mac approval and a complete desktop walkthrough were unverified. Consult the [release evidence](release-notes-0.1.0a2.md#release-evidence) for later results tied to the exact archive. A familiar version number alone is not sufficient: retain the release commit, runtime identity and archive fingerprints. See [verification](verification.md) and [release controls](release-controls.md).

When the official example is missing locally, the built-in example makes an external download request after the user selects the download action. It obtains the pinned official World Bank workbook; the request sends no analytical workbook, scenario inputs, results or notes. The publisher receives ordinary connection metadata such as an IP address. Prepared case definitions are bundled with the app, and a verified local workbook copy is retained for reuse. Source checks and a successful example download are distinct from observing all outbound traffic during normal use, failures and diagnostics. Representative offline operation and connected outbound observation remain separate evidence work.

A future hosted illustrative calculator needs its own assessment. A static documentation website is not that calculator, and neither establishes that confidential workbooks can be processed safely on a server.

## How we handle technical choices

We seek to follow the standard's spirit while building something stakeholders can actually use. We do not yet know whether any specific requirement would lead to a material conflict with that goal. We will investigate rather than assume either perfect alignment or a conflict.

For a consequential choice, record the requirement being considered, the stakeholder benefit, available alternatives, what data moves and who controls it, safeguards and their test evidence, residual limits, accessibility, maintenance cost and the reason for the chosen approach. If a choice leaves a formal requirement unmet or uncertain, say so here. Practical alignment is not a substitute for meeting the criteria if we later seek recognition.

For example, current scenario exchange uses an inspectable file and requires the identical workbook. That supports reuse without introducing shared online storage. It also limits convenience: users cannot automatically translate a scenario to another baseline or year sequence. This is a product trade-off, not evidence that the DPG Standard requires a particular exchange design.

Open assessment rows are not automatically release blockers. Real confidentiality defects, unsupported redistribution rights or misleading analytical claims still require correction or a narrower offered scope. A disclaimer cannot replace a safeguard. Formal nomination remains optional; it is not a promised outcome of this preview.

## Preserve these boundaries as the tool develops

Scenario exchange must continue to select only deliberately shared fields, identify its format, years and workbook, and treat imported text and evidence as untrusted. Import creates inputs to review and calculate; it must never confer verified-result status. Existing private journals must not silently become shared explanations.

Before offering hosted calculations, separately verify server-enforced input restrictions, visitor isolation, bounded work queues, retention/deletion and logs. The initial hosted scope is the official illustrative workbook only, with a clear notice that entered assumptions are processed on the server. Do not infer these protections from the local application's tests.

The release maintainer assembles the exact source, documentation, dependency and artifact evidence; a separate reviewer evaluates it. Teal Insights owns the project assessment and any eventual nomination. Confidential workbooks, internal paths and private review records stay out of public evidence. [Feedback](feedback.md) can help us improve this mapping and identify practical needs we have missed.
